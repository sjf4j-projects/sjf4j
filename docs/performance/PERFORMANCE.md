# Performance

Performance comes first. Explicitly disclose changes that may regress performance, including generated code, even when the change looks like a simplification.

## When to benchmark

- Documentation and refactors that preserve runtime hot paths and executable generated bytecode do not require a performance run. Inspect generated code/bytecode when relevant.
- Changes to hot paths, generated code, allocation, dispatch, or backend calls require a focused benchmark when the impact is uncertain. Do not run Full for every PR.
- Run Full at release milestones or when refreshing a suite's published results. Smoke timings are not performance measurements.

## Baselines and history

Maintain independent rolling baselines per **exact CPU model, execution mode (JVM or Native Image), suite and backend/group**. EPYC 7763, EPYC 9V45, EPYC 9V74 and Xeon 6975P-C are separate environments.

- Record source SHA, date/run, exact CPU per backend/group, OS/architecture, JDK or GraalVM build, dependency versions, JMH profile, inputs/seeds, and aggregation method. Retain latency, allocation where supported, fork/process results and links to raw artifacts.
- Compare each exact case with the latest accepted matching CPU baseline, not simply the last run. Match workload, parameters and measurement protocol. Disclose JDK/dependency changes; do not attribute their effects to SJF4J without isolation. Changed profiles or fixtures need a new baseline.
- Name dated reports `YYYY-MM-DD-vX.Y.Z[-snapshot][-mode][-run-id].md` in the suite directory (e.g. `2026-11-12-v1.5.1-snapshot.md`). Use lowercase `snapshot`; distinguish `jvm` and `native` where needed. Add the workflow run ID to disambiguate reports with otherwise identical names. Keep CPU models and serial/parallel execution details in the report and index, not the filename.
- Preserve dated reports in the existing suite directories; update only the matching CPU/backend/group index after review. Never replace other CPU entries or silently accept a suspected regression. A new CPU establishes its own baseline once a valid result is accepted. Missing CPU metadata is not a match.
- Shared runners provide rolling diagnostic baselines, not controlled release measurements. Same CPU does not guarantee identical frequency, load, VM or JIT behavior. Do not infer regressions from cross-CPU deltas, including speedup ratios.

## Report retention

Keep history small and curated. Commit a dated report only after explicit acceptance: the intended Full suite completed, correctness and completeness checks passed, environment and results were reviewed, and any material regression was explained or explicitly accepted. Retain reports for release milestones, new CPU baselines, or meaningful confirmed performance changes; do not archive every repeated run.

Keep experimental, failed, partial and redundant runs in Actions artifacts. Record useful confirmed diagnostic conclusions briefly under Known performance characteristics with run links, rather than creating separate reports. Do not routinely commit raw JMH dumps, JIT logs or binaries. Update the baseline index only for accepted results.

## Regression review

**Relative performance is the primary metric.** Always compute ratios within each run first, then compare those ratios with the latest accepted same-CPU baseline for every matching case.

- Compare equivalent third-party implementations against SJF4J Runtime and Compiled separately (e.g. Native / Runtime, Native / Compiled, Blackbird / Runtime, Blackbird / Compiled, MapStruct / Compiled).
- Compare Runtime / Compiled wherever both are available, even if third-party controls exist. Use comparable semantics, representations and measured operations; distinguish CAST and STRICT, or binding-only and binding-plus-validation, explicitly.
- For latency, ratio = reference latency / SJF4J latency; for throughput, ratio = SJF4J throughput / reference throughput. Higher is better. Relative change = (candidate ratio / baseline ratio - 1) × 100%. Report old ratio, new ratio and relative change for matching cases; do not rank changes by absolute latency or average unrelated workloads.
- Report B/op independently (including relative allocation ratios where meaningful); retain absolute latency, raw fork/process data and allocation for diagnosis and reproducibility. Absolute cross-run latency changes are not the primary review metric.

A relative performance decline greater than 3% is a signal to investigate, not automatic proof. Inspect independent forks/processes, changes in the third-party control and allocation before attributing the decline to SJF4J. Also disclose material allocation regressions or known slow paths. Run a focused same-runner A/B only for material unexplained signals or when causality needs confirmation. Follow each suite's documented aggregation; do not mix profiles or metrics. For unstable JIT outcomes, retain all fork means and use separate diagnostics rather than treating trimmed scores as proof.

Record known CPU/JIT-sensitive behavior with scope, evidence, unresolved questions and the chosen implementation. Do not repeat the same investigation without new evidence (changed hot path, materially worse result on the same CPU, or a new relevant JDK/backend). Keep unresolved cases visible; do not use them to excuse unrelated regressions.

Allocation was unchanged. On Intel, #398 improved Users 1KB; restoring instance methods or explicit null branching was slower than the current static helper. AMD regression is observed but its cause is unresolved; CPU/JIT interaction is a hypothesis, not proof. [AMD follow-up](https://github.com/sjf4j-projects/sjf4j/actions/runs/46108778459) obtained no matching runner and produced no benchmark result.

Keep the current compile-time null policy and static string-member helper. Do not revert based on cross-CPU measurements. Reopen the AMD investigation only with new comparable evidence or a relevant hot-path change. These targeted diagnostics are not Full baseline replacements.
